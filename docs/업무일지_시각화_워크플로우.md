# 업무일지 및 업적 시각화 워크플로우

## 목적

현재 프로젝트에서 진행하는 일련의 작업을 단순 작업 로그로 흘려보내지 않고, 일간 업무 일지 형태로 정리한다. 이후 이 기록을 기반으로 업무 성과, 자동화 기여, 데이터 정리 성과, 산출물 제작 성과를 시각화할 수 있게 만든다.

## 현재까지의 작업 기록

### 2026-05-27

#### 1. 실습자료 정리

- macOS에서 넘어온 한글 자모 분리 형태의 폴더명을 Windows에서 자연스럽게 보이도록 정규화했다.
- `실습자료들` 내부 중복 파일을 SHA-256 해시 기준으로 확인했다.
- 완전히 동일한 중복 파일 3개를 제거했다.
- 모듈별 하위 폴더에 흩어져 있던 실습 파일 15개를 `실습자료들` 최상위로 이동했다.
- 비워진 기존 모듈 폴더를 삭제했다.

#### 2. 시각화 후보 데이터 선정

- CSV 파일 5개를 확인했다.
- 행 수, 날짜 컬럼, 숫자 지표, 범주형 컬럼, 대시보드 스토리 가능성을 기준으로 후보를 비교했다.
- `장비유지보수_2022-2024.csv`를 최종 시각화 데이터로 선정했다.
- 선정 이유:
  - 229행으로 데모용 대시보드에 충분한 데이터 규모
  - 날짜, 장비, 설치위치, 이상유형, 담당자, 수리시간, 비용, 부품교체여부 컬럼 보유
  - 비용 추이, 고장 원인, 설비별 비용, 위치별 분포, 상세 내역을 한 화면에 구성 가능

#### 3. 대시보드 기획

- `장비 유지보수 CSV 시각화 대시보드 계획`을 수립했다.
- 단일 HTML 파일 방식으로 결정했다.
- CSV 데이터는 HTML 내부 JavaScript 배열로 내장하는 방식으로 결정했다.
- 외부 서버, npm, Python 실행 없이 브라우저에서 열 수 있는 산출물로 범위를 정했다.
- 계획 문서를 `docs/장비유지보수_대시보드_계획.md`에 저장했다.

#### 4. 대시보드 구현

- `실습자료들/장비유지보수_대시보드.html`을 생성했다.
- 원본 CSV 229행을 HTML 내부 `maintenanceData` 배열로 내장했다.
- 구현 항목:
  - 총 유지보수 비용 KPI
  - 총 건수 KPI
  - 평균 수리시간 KPI
  - 부품교체율 KPI
  - 월별 비용 및 건수 추이 차트
  - 비용 상위 장비 차트
  - 이상유형 Top 차트
  - 설치위치별 건수 차트
  - 상세 내역 테이블
  - 연도, 설치위치, 이상유형 필터
  - 필터 초기화 버튼

#### 5. 검증 및 실행

- 전체 데이터 기준 KPI를 검증했다.
  - 총 건수: 229건
  - 총 유지보수 비용: 68,233,000원
  - 평균 수리시간: 2.93시간
  - 부품교체율: 34.9%
- 필터 동작을 검증했다.
  - 2024년 필터: 73건
  - 2024년 + 생산2동 필터: 27건
  - 초기화 후 전체 229건 복귀
- 인앱 브라우저의 `file://` 제한을 피하기 위해 임시 `localhost` 서버로 HTML을 띄웠다.

## 앞으로의 일간 업무 일지 양식

새 작업을 할 때마다 아래 형식으로 기록한다.

```md
## YYYY-MM-DD 업무 일지

### 오늘의 목표

- 

### 수행 작업

- 

### 생성/수정 산출물

- 

### 검증 결과

- 

### 업무 성과 요약

- 정리한 파일 수:
- 제거한 중복 수:
- 생성한 산출물 수:
- 자동화/시각화한 데이터 수:
- 검증한 지표 수:

### 다음 액션

- 
```

## 업적 시각화 기준

업무 일지를 바탕으로 아래 지표를 시각화한다.

- 작업량: 수행 작업 수, 처리 파일 수, 생성 산출물 수
- 데이터 정리 성과: 정규화한 파일/폴더 수, 제거한 중복 수, 구조 단순화 정도
- 분석 성과: 검토한 데이터셋 수, 선정한 데이터셋 수, 도출한 KPI 수
- 구현 성과: 생성한 HTML/문서/리포트 수, 구현한 차트 수, 구현한 필터 수
- 검증 성과: 실행한 검증 수, 통과한 검증 수, 확인한 핵심 지표 수
- 재사용성: 문서화한 계획 수, 워크플로우 수, 다음 작업에 재활용 가능한 템플릿 수

## 대화 및 답변 규칙

- 사용자가 별도로 바꾸기 전까지, Codex 답변의 마지막에는 이모지 3개만 붙인다.
- 이모지는 답변 분위기에 맞게 고르되, 개수는 항상 3개로 유지한다.
- 업무 기록이나 문서에는 필요한 경우 이 규칙을 명시하되, 본문 곳곳에 불필요한 이모지를 남발하지 않는다.

## 운영 방식

- 작업을 마칠 때마다 업무 일지에 반영할 수 있는 형태로 요약한다.
- 큰 작업은 `계획 → 구현 → 검증 → 업무일지 반영` 순서로 정리한다.
- 시각화 대상이 될 수 있는 숫자 지표는 가능하면 함께 남긴다.
- 추후 요청 시 이 문서를 기준으로 일간/주간 업무 성과 대시보드를 만들 수 있게 유지한다.
